Decisions made July 2026 for `design/plan-infraUpgrade.md` Phase 7:
- The ARM k3s spot cluster (k8sarm01–04) and all arm32 support are being retired; arm64 workloads move to a new EKS Auto Mode cluster (arm64 spot NodePool, k8s 1.36).
- **User chose eksctl (ClusterConfig YAML + a `build/eks.py` wrapper) over Terraform** to match the repo's declarative-config-plus-CLI pattern (`build/aws.py`, `build/dns.py`). Don't propose Terraform/OpenTofu for this repo without new justification.
- The `apama-windows` EKS cluster (`common/kubernetes-reference/win-cluster.yml` etc.) was an old experiment, no longer needed — being deleted (plan Phase 7e). The `bm-win2019` k3s worker is unrelated and stays.

**Why:** keeps a single tooling style in the repo; eksctl prior art already existed (`win-cluster.yml`).
**How to apply:** when implementing Phase 7, put eksctl config in `eks/aws-reference/`, NodePool/coredns manifests in `eks/kubernetes-eks/`, and keep day-2 eksctl changes human-triggered.

VPC survey (July 2026, done via a scoped read-only IAM user + full network dump — see `eks/aws-reference/network-dump/SUMMARY.md` in the `dev/eks-arm-cluster` branch): one VPC (`vpc-07ed1b105673dc444`), CIDRs 10.78.134.0/24 + 10.78.136.0/24 (VPN /25, NAT GW /28); on-prem 10.20.0.0/15 via VGW (main/implicit route table `rtb-0e32a1bf16d6bd7a1`); svnsync EBS volume in AZ 1c. The "colo-transit-gateway" (`tgw-088a9a2fbeeed5052`) has a cross-account attachment to account `905418157859` — confirmed via 90-day CloudWatch BytesIn/BytesOut (zero throughout, zero blackhole drops) to have **never carried traffic**. **Decision: keep the TGW attachment (don't delete — avoids ever redoing cross-account acceptance), shrink its footprint instead** by moving its AZ-1a ENI from a /26 to a new minimal /28 (`10.78.134.16/28`) via `modify-transit-gateway-vpc-attachment`. This frees **Layout B**: `10.78.134.128/25` (AZ 1c) + `10.78.134.64/26` (AZ 1a) — no secondary CIDR needed. EKS API access: private-only, restricted to colo `10.20.0.0/15` + Client VPN pool `10.78.128.0/22` (`cvpn-endpoint-0cde500392dd5def2`). CrowdStrike Falcon works on Bottlerocket in BPF mode (vendor TAM confirmation still pending — public docs only). arm32 dev envs + arm qatv confirmed unused, dropped from migration scope entirely. TeamCity will use its native Amazon EKS auth option. apama-windows EKS cluster no longer exists in AWS (git artifacts only, being deleted). EKS upgrade cadence is a design requirement (extended support ≈6× control-plane fee) — build/eks.py warns when nearing end of standard support.

Single-stack decision (2026-07-13, PR 917 discussion): the CloudFormation stack is named **`apama-estate`** (renamed from arm-network before creation — stacks can't be renamed) because the eventual T-608 estate import targets this SAME stack: one repo-driven template holds both the project-created subnets and the imported pre-existing estate. User explicitly preferred one stack over the two-stack permission-separation design; accepted trade-off is the nightly build user's CFN grant covers the combined stack (changesets + PR review are the gate). Also from PR 917 review: apama.com IS split-horizon (publichttp.apama.com aliases like teamcity.apama.com differ internally) → CoreDNS forwards apama.com+apama.dev only to 10.21.65.45, everything else via VPC resolver. svnsync has NO S3 usage (Pod Identity removed entirely). IGW exists (earlier "no IGW" claim was wrong; natGW subnet is public). dockerd-lnx-arm64-dev added (general-access arm64 dockerd, T-410).

Access design (decided 2026-07-11): apama-arm **will be imported into Rancher** (the org's normal management plane) — Rancher-proxied kubectl is the primary human access path; direct access via the shared admin SSO role's cluster-creator entry (`bootstrapClusterCreatorAdminPermissions`, bootstrap must run from that SSO role) is the fallback. Admins are deliberately NOT listed in `accessConfig.accessEntries` — only the production build user (cluster-wide edit) and the TeamCity agent-launch user (edit, `build-agents` namespace). One-off `eksctl create cluster` runs under human admin credentials; the standing build user's policy (`eks/aws-reference/iam-policy-eks-apply.json`) covers steady-state only. `build/eks.py` additively reconciles access entries + Pod Identity associations (never deletes); endpoint/VPC/Auto Mode settings stay warn-and-human.

**The actual TeamCity agent that runs `build.py`/`build/eks.py` in production is `build-debian12-tiny` (a size variant of `build-agents/docker-amd64/Dockerfile.build-debian12`)** — confirmed by the user 2026-07-10 after an initial wrong guess sprayed `eksctl` across three unrelated shared base images (`common/docker/Dockerfile.common-{ubuntu2004,rhel8,rhel9}`, since reverted). `awscli` on that image comes from a declared package in `ansible/kubernetes/ansible/files/packages/build-environment.yml` (applied by `common-debian12`'s `setup-environment.sh`), not a raw curl install — but `eksctl` has no apt package, so it was added as a `curl`+`tar` GitHub-release install directly in `Dockerfile.build-debian12`, mirroring that file's existing `fnm` install pattern.
